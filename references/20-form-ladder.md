## B. 고르는 법

위 칸부터 내려가며 **"이 칸으로 v1 완료 기준 5개(`templates/v1-plan.md` §7)를 채울 수 있나?"** 첫 번째로 "예"인 칸을 고른다. v1-plan §4 에 "위 칸을 안 쓴 이유" 한 줄을 남긴다.

자주 나오는 판단:

- **고객 데이터가 이미 Supabase 에 있으면 칸 4 가 칸 2 보다 가벼울 수 있다.** 데이터를 시트로 옮기는 일 자체가 새 손일이 되기 때문이다.
- **맥이 꺼져 있어도 돌아야 하면**(매일 아침 9시 리마인더 등) 칸 1 보다 칸 2.
- **판단이 섞인 초안**(리뷰 답글·문의 분류)은 칸 1. 규칙으로 끝나는 일(기한·재고 기준)은 칸 2.
- **공식 연결이 있으면 칸 3 을 쓰지 않는다.** 칸 3 은 연결이 없을 때만.
- **이미 있는 무료 도구가 그 일을 하면**(근태·명세서 발송) 칸을 고르기 전에 그 도구를 권한다 (`11-ops-catalog.md` 「쓰기 먼저」).

## C. 저장소에 연결하는 규칙

**기본은 기존 프로젝트 저장소다.** 코드가 없는 형태(칸 1·2·3)도 저장소에 흔적을 남겨 v2·v3 로 이어지게 한다.

| 무엇 | 어디에 |
|---|---|
| 운영 지도·기획안·log | `docs/ops-os/` |
| 예약 작업 프롬프트 사본 | `ops/scheduled/<이름>.md` |
| Apps Script 사본 | `ops/apps-script/<이름>.gs` (시트에 붙여 넣은 것과 같게 유지) |
| 브라우저 탐색 기록·스크립트 | `ops/browser/<이름>.md` · `ops/browser/<이름>.mjs` |
| 예약 작업이 만든 준비물 | `docs/ops-os/out/` — 개인정보가 들어가면 `.gitignore` |
| 키·비밀번호·로그인 파일 | **저장소에 두지 않는다** (환경변수 · Script Properties · `~/.ops-os/auth/`) |

## D. 새 저장소를 추천하는 조건 (하나라도 맞으면)

1. **쓰는 사람이 다르다.** 직원·알바·거래처가 쓰는 화면이고 랜딩 사용자와 무관하다.
2. **민감한 데이터다.** 급여·직원 정보·세무 자료이고, 랜딩 저장소가 공개이거나 랜딩 DB 와 섞이면 안 된다.
3. **다른 사업·브랜드의 일이다.**

추천만 하고, 만드는 것은 승인 뒤에 한다. 순서:

1. `git init`
2. `.gitignore` — `.env*` · `.claude/settings.local.json` · `node_modules` · `.vercel` · `auth*.json` · `docs/ops-os/out/`
3. `gh repo create <이름> --private --source=. --remote=origin`
4. 첫 커밋 + push

그리고 기존 저장소 `docs/ops-os/00-map.md` 8절(갱신 기록)에 새 저장소 이름을 적어 두 곳을 잇는다. 데이터는 새 Supabase 프로젝트나 별도 시트로 분리한다.

## E. 코드 저장소가 아예 없을 때

세금계산서만 덜고 싶은 경우처럼 랜딩과 무관하면 **칸 1·2 로 코드 없이 끝내는 것이 기본**이다. 상태 파일은 `00-detect.md` §1 규칙대로 사용자가 정한 폴더의 `docs/ops-os/` 에 둔다. 나중에 v3 로 한 화면이 필요해지면 그때 새 저장소를 추천한다.
